## Ограниченный прототип

`LLAMA_DSPARK_GPU_FEATURES=1 LLAMA_DSPARK_GPU_FEATURES_ASYNC=1` задаются до запуска процесса; это переменные окружения. Async требует уже включённого bridge. Установка только ASYNC ничего не включает.

- Packed source остаётся в owned backend/stream target output CUDA5; encoder input - в CUDA0.
- Input использует существующий `ggml_backend_tensor_copy_async`. Source stream читает packet до следующего pack в тот же storage; destination stream ждёт copy-event до FC. Новые CUDA kernels и дополнительные payload buffers не нужны.
- Допускается прямой поддерживаемый encoder MUL_MAT, его backend закреплён за CUDA FC. Непрямой/scaled/LoRA FC и несовпадение buffer/backend используют прежний sync fallback. Token-input ветки не получают backend pair. Feature-update injection при generation проходит тот же encoder path и тоже может использовать async.
- Backend bindings учитываются при graph reuse; при unbind сначала синхронизируется draft. Target context и backend mode должны жить до unbind. Действующий common lifecycle соблюдает этот порядок.
- Однократный `async packed feature copy active: CUDA5 -> CUDA0` подтверждает фактический вход в async API; он проверен в полном ON-запуске. Это не заявление о прямом аппаратном P2P: NVML сообщает CNS/NS, CUDA может выполнять host staging.

```mermaid
flowchart LR
    subgraph Source[Owned source stream CUDA5]
        P1[Pack A] --> C[Copy A to input] --> P2[Pack B / reuse packet]
    end
    subgraph Encoder[Encoder stream CUDA0]
        E[Wait copy event] --> F[FC A]
    end
    C --> E
```

Снято CPU-ожидание непосредственно внутри input copy, но следующий sync pack всё равно ждёт освобождения того же packet на owner stream. Физическая стоимость29ms не исчезает; эта версия даёт лишь ограниченную возможность перекрытия. Отдельный новый Nsight profile async-пути не снимался; end-to-end результат измерен без profiler/interposer. Нельзя считать enqueue latency итоговым ускорением PP.

## Корректность и память

Реальный `llm_graph_input_embd` проверен на CUDA5 -> CUDA0:40 cases, sync/async и2 mismatch-fallback режима; rows1/4/6/7/508/512/513/1024/8192 и513 replay. Producer pack и consumer snapshot выполнялись разными CUDA backends. Source packet перезаписывался до drain consumer; payload, sink bounds и внешние input canaries exact. Consumer metadata сохранялась до завершения GPU. [Source и результаты](artifacts/input.json).

Это packet/input проверка, а не новый полный joint draft KV/logits/rollback gate. Прежние target native hashes не перепроверялись в этом этапе; target arithmetic/quant weights не менялись. NLL/PPL не запускался. Для promotion после будущего положительного speed gate нужны joint state/logits/rollback и длинный контекст.

No_alloc SYNC/ASYNC: model/context/compute budgets одинаковы на всех6 GPU, delta0. Дополнительной памяти сверх уже имеющихся510.02MiB GPU bridge не требуется. Полный A/B также сохранил model buffers/offload и minimum free1157.38MiB в обоих режимах, выше512MiB. Оба процесса exit0, без compute-size mismatch/OOM/CUDA errors/forced kill.

## Стоимость producer-local кандидата

После полного A/B, на свободных GPU, отдельно измерены предполагаемые payload частей:

| Payload | Sync completion median | Async completion median |
|---|---:|---:|
| CUDA5 -> CUDA0,30MiB |29.35ms|29.56ms|
| CUDA4 -> CUDA0,20MiB (taps37/38) |6.93ms|7.02ms|
| CUDA5 -> CUDA0,10MiB (tap39) |9.81ms|9.86ms|

Все payload/canaries и reuse guards exact. Измерены отдельные transfers, их совместное перекрытие не проверялось. Эти цифры оправдывают prototype с producer-local retention, но не являются прогнозом PP: ещё нужны packing, merge, events и реальный VRAM budget. Избегать переноса полного retained buffer на ранний GPU во время target prefill: предыдущий [consumer-buffer эксперимент](../1017-gpu-feature-transfer-20261102/REPORT.md) уже показал потерю overlap.
