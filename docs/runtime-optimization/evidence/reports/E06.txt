# Завершение калибровки и startup auto MoE prefill — 2026-10-30

Runtime закоммичен в `my_maya`: **e4d423309**. Ниже сохранён отчёт о проверенной worktree-сборке; её source/binary hashes и состояние до коммита находятся в raw manifests. `my_build` не менялся.

## Результат

На `my_maya` реализован opt-in `LLAMA_MOE_PREFILL_STAGE=auto`: runtime сам снимает калибровку при загрузке, выбирает CPU или существующий pinned staging и сохраняет costs рядом с первым GGUF-шардом. В данной Q3 конфигурации выбран CPU: prefill ускорился на **45.05% при512** и **40.85% при8K**, TG изменился менее чем на0.1%. Диагностический NLL-гейт +0.01 nat/token пройден на тексте и коде; Top-1 и canonical KV state совпали.

Ветка `my_build` сохранена: `c19cdd742b947693ff81e54407b914f5c06f92a0`. HEAD `my_maya`: `23d3e99a416d699d2edb4b81bffba6c1b986947f`; работа остаётся в worktree. Автоматического включения staging для всех запусков и merge нет. Ранее запрошенный пользователем default ON `LLAMA_DSV41_VERIFY_QUANT_SAMPLES` сохранён в обоих путях сравнения.

## Два найденных дефекта

1. **В probe v1 входы задавались только один раз.** Allocator вправе повторно использовать storage после последнего читателя. Последующие проходы получали изменённые activations/router logits. Это дефект диагностического калибратора. В native probe и startup benchmark inputs/logits/IDs теперь загружаются перед каждым исполнением, вне таймера. На исходном layer39/N512 reproducer max_abs CPU/GPU уменьшился с50.6006 до0.0321868, relative L2 — с~1.8666 до~0.01259. Resident/serial-copy GPU max_abs=0. Старые raw результаты сохранены; version1 costs не переиспользуются.
2. **Stock scheduling host weights не означает CPU execution.** `ggml_backend_sched_backend_id_from_cur` может offload-ить host `MUL_MAT_ID` на CUDA при большом batch. Первый прототип auto лишь оставлял stock path, хотя измерял принудительный CPU. Исправленный auto явно назначает CPU для host-проекций, если CPU выиграл. В контрольном prefill512 gate/down39 выполнялись на GPU (2 projections), в auto — на CPU (2); при8K зафиксировано32/32. Resident projections остаются на своих GPU. Это основной источник выигрыша; новый CUDA kernel не добавлялся.

Первый прототип хранится отдельно в `full/`: там скорости почти совпали, так как fallback ещё не назначал CPU. Его результаты не смешаны с итоговым `full-cpu-lane/`.

## Калибровка фактических lanes

Native probe v2 измеряет `gpu_resident`, принудительный `cpu_lane`, отдельный `serial_h2d_gpu` diagnostic и production `pinned_staged`. Последний включает grouping/packing, pinned double buffering, H2D, существующие quantized kernels и возврат результата на home GPU. Для другого destination учтены scheduler/P2P transfers. Полные reference tensors нужны только внешнему diagnostic probe; production startup использует уже загруженные tensors и ограниченный scratch.

Снято24 FFN nodes: activations/raw router logits/Top-K на слоях0/39, текст/код512/8K. Неконтинуальный Top-K сохранён с учётом strides. Реальная calibration серия использует слой39, который здесь является host-spill слоем, widths33/128/512: 36 cases на трёх destinations. Callback capture отделён от измерений. GGUF подтверждает sqrt-softplus gating4, weights norm=true, scale1.5, clamp10 во всех40 слоях — это настройки диагностического graph; startup берёт фактические hparams загруженной модели.

## Runtime interface и persistence

```bash
LLAMA_MOE_PREFILL_STAGE=auto ./llama-server ... --moe-expert-cache 64
```

При MiB/device интерфейсе cache тоже может быть включён. `LLAMA_MOE_PREFILL_STAGE_DEVICE` сохраняет явный manual override. `LLAMA_MOE_PREFILL_STAGE_COSTS` — необязательный другой путь; Python и предварительный запуск внешнего probe не требуются.

Файл по умолчанию: `<first-shard>.moe-prefill-costs.json`. В выполненном тесте создан:

```text
/mdd/D2W/models/smalinin/DeepSeek-V4.1-Flash-1017/DeepSeek-V4.1-Flash-1017-Q3_K-AntirezLike-00001-of-00010.gguf.moe-prefill-costs.json
```

Режим измеряет loaded expert tensors: chunk512, batch CPU threads, synthetic seed42/equal logits/rotating IDs, warmup2+3. Это отдельные FFN graphs без KV decode и без изменения LRU/route counts. Для GPU нужен выигрыш не менее5% относительно CPU на каждом поддержанном host слое группы, плюс scratch/cache headroom и1024MiB reserve. До выбора любого destination учитываются будущие кеши всех cache homes, затем выбранные staging workspaces; сложение budget защищено от overflow. При выигрыше CPU его backend назначается явно. Короткие prefill tails33..511 используют CPU; decode/verification<=32 сохраняют существующий cache path. Manual `=1` сохраняет прежний диапазон33..512. Неподдержанные типы/архитектуры сохраняют stock scheduling.

Identity включает runtime/shared-library hashes, GGUF shard stats, metadata, реальные layout/type/buffer placement и sampled expert bytes, фактические FFN hparams, CPU/affinity/NUMA/governor/threads, GPU UUID/PCIe/driver и протокол. Sample hashes не являются полным checksum checkpoint. Проверяется неизменность identity до публикации. Совпадающая запись перепроверяет CPU и лучший доступный cached GPU; использовать можно только перепроверенный GPU. Дрейф >25% или20us, изменение identity или появление ранее непокрытого доступного GPU вызывает новый полный замер. Проверки выполняются вне request PP/TG.

Файл checksummed; запись через временный файл/fsync/atomic rename и directory lock. Повреждённый/foreign/symlink cache сохраняется; замер доступен в памяти. При чужом lock — CPU fallback без конкурирующей калибровки. Read-only каталог явно сообщается в логе. Внутренний CPU backend вызывается через registry API, без новой прямой CPU-plugin зависимости в libllama.

Первый metadata-fit ещё не имеет measurements: он планирует CPU prefill и консервативно резервирует возможный workspace/graph temporary на всех CUDA candidates. Metadata не измеряет и не пишет costs. Real startup фиксирует выбранный путь на время жизни cache owner. Это замена исходного предложения об одном заранее известном GPU в metadata/real: при самостоятельной первой калибровке такого выбора ещё нет.
