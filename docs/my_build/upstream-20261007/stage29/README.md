# Stage 29: GLM5NEXT cache reproducibility

Source base: committed Stage28 fix 5a4de37b8. No production code changes. Reuse the immutable Stage28 final binary snapshot; verify all library and affected source hashes before launching. Installed server and presets stay unchanged.

`run-server.py` reuses the Stage2/baseline server lifecycle, GPU placement and request plumbing. Four initial configurations: DFlash and MTP, each with pool-cache on/off. All requests are fully sequential and use fixed slots. Three short prompts are the Stage28 prompts; a fourth contains 24 numbered facts. Each prompt has fresh1, reuse1, reuse2 and fresh2 responses. The first three prompts are interleaved by phase and slot, so returning sequences exercise idle-slot cache handling; cache_n determines whether tokens were actually reused; the long prompt repeats in slot 0. Requests are greedy with seed 1234, at most 64 output tokens and top-5 pre-sampling probabilities. These probabilities are not full logits. No concurrent-request equivalence is inferred.

Server configuration: unified KV, three slots, context 8192, batch 2048, ubatch 64, F16 KV, explicit six-GPU UUID order, layer split 1,1,1,1,1,0.4 and fit off. CUDA graphs retain the default. RAM prompt cache is explicitly 2048 MiB, idle-slot caching enabled, verbose server events recorded. `cache_prompt` toggles prompt reuse per request; LLAMA_GLM5_POOL_CACHE toggles pooled indexer-key reuse across independent server processes. These are different caches. Native controls are available if observed differences require them. GPU processes run sequentially.

`run-cpu.py` builds a standalone harness using the existing tiny GLM5NEXT GGUF from test-llama-archs. CUDA devices are hidden. Four cases cover unified/separated KV and pool-cache on/off. Save all three sequence states after independent prefixes of 96/128/160 tokens. Compare a fixed 20-row continuation with restore into the same context twice and into a new context. A separate three-step tail produces 9 rows and compares direct continuation with tail rollback and with a saved-state restore. Every row contains all 128 logits. The harness uses deterministic forced token IDs so a numerical difference does not alter subsequent inputs. It does not add files to tests/.

`analyze-results.py` records exact equality, first differences and cache/prefill counts for real responses; CPU comparisons record full-logit equality, max absolute and RMS differences and greedy token agreement. Numerical differences are reported without silently imposing a tolerance. CPU arithmetic is not a substitute for real CUDA validation.

Raw server logs, binary cache buffers and logits remain in the workspace. The repository archive contains scripts, manifests, request/response JSON, comparisons and file hashes. Use a new output directory for reruns; scripts reject existing run directories.

The fixed-slot short prompts produced cache_n=0. Only their long-prompt repeats exercised a real checkpoint restore. `run-ram.py` therefore adds one DFlash and one MTP process with three distinct long prompts and automatic slot selection. The requests remain sequential; each RAM process has 12 responses. It uses run-server.py without editing that driver and records both source hashes. All six reuse requests must have positive cache_n and logs must show actual RAM prompt restore, otherwise that coverage is not claimed. No native controls are needed if the cache comparisons match.

Probability coverage: speculative responses contain 64 probability objects but most have empty top_logprobs and placeholder logprob 0. Only nonempty rows count as numerical observations. The archive keeps their indexes and values. Matching complete response fields does not establish full CUDA-logit equality for every generated token.

RAM-restore comparisons diverged for DFlash and MTP while fresh repeats matched. `run-ram-controls.py` adds exactly two controls using the same RAM request handler: DFlash with pool-cache off and native with pool-cache off. Server result status passed means all HTTP requests finished, not that reproducibility passed. Exact-answer and numerical comparison fields in summary.json determine the latter. No production fix is included in this stage.
