Ask decisions и вычисления не изменены. Две папки бинарников зафиксированы по SHA; результаты исходных запусков сохранены. После исключения тестовый процесс завершается; восстановление precision/временных данных на ошибочном пути этой диагностической обвязки не сертифицировано.

## Обнаруженная граница cache state

Первый N=1 процесс завершил восемь коротких запросов и свежий dense prompt3033, все девять ответов точны. Следующий `dense-cache` получил HTTP500: `decode() failed: unsupported cache extent`. Перед отказом успешно обработаны последние4 prompt tokens на позициях3029..3032 без диагностических замен.

Отдельный N=1 процесс завершил оставшиеся свежие ratio1/ratio2 запросы и воспроизвёл отказ на `ratio2-cache`. Захват:

```
DS21_EXTENT layer=q-0 (view) (permuted) pos=6617 width=2 raw=256 raw_limit=768 total=256 compressed=0 error=unsupported cache extent
```

На первом raw attention слое source K имеет256 строк, физический storage768. Правило callback `min(raw_limit, pad256(absolute_position+1))` требует768 и правильно останавливается на guard. Ослабление guard или добавление padding без проверки native не выполнялось.

`llama_kv_cache::get_n_kv()` использует округлённый physical `cells.used_max_p1()`. При sequence restore `state_read_meta()` размещает восстановленные строки через `find_slot()`. Это объясняет, почему одинаковая absolute position не задаёт одинаковый padded raw extent после восстановления. Причина относится к ограниченной политике диагностического callback; native и оба off-контроля эти cache requests выполнили.

N=3 завершил все 11 свежих запросов, затем воспроизвёл тот же отказ на ratio2-cache: position6617, width 4, raw256, raw_limit768, total256, compressed0. Все 11 свежих ответов точны. Три cache requests завершились HTTP500; это отказы совместимости, а не успешные выходные сравнения.

В N=1 длинные batches имеют width 2. В N=3 widths 2/3/4, преимущественно 4. Это счётчики effective per-query predicate, установленного этапом20, без дополнительного profiler запуска. Анализ predicate учитывает только width>1: raw_limit инициализируется scalar_attention, а observer width 1 для покрытия не используется. В каждом успешном широком decode attention и upgate заменяются40*width раз, matmul4*40*width+7*width; prefill interventions равны 0. Raw crops в длинных окнах равны 0, поскольку fresh raw extent уже 768; compressed padding меняется на проверяемых границах.

Все шесть длинных fresh ответов имеют одинаковый native prefix 128: token-ID SHA256 `82b363a4bb78b5eeb85bfa9890c657f1e555871c56bb9a1a0e2db3b757dd172a`. Это повтор одного задания при разных длинах фона, не оценка качества разных задач. На этих длинных запросах принято 38/89,38/89,36/91 draft tokens для N=1 и 54/216,52/222,50/228 для N=3. Диагностические timings включают повторную callback-работу и не измеряют production speedup.

## Решение перед следующим этапом

Свежая greedy генерация проходит расширенный набор, включая реальные dense/sparse переходы. Повторное использование кэша с DSpark пока несовместимо с абсолютной формулой raw extent. Одного clamp к текущему source raw size недостаточно для утверждения общей совместимости: нужно сохранить per-query размеры и при последующих физических переходах256/512.

Следующий шаг после review - согласовать raw extent с физическим состоянием KV после restore, проверить полные native/wide logits и повторить шесть cached speculative сценариев с сохранением предыдущих SHA. Затем можно переходить к CUDA-реализации без callback duplication и проверке production correctness/throughput. Произвольная compaction, saved-session restore, multi-slot, другие KV типы и sampling distributions по-прежнему не покрыты.

Итог этапа подготовлен для review перед коммитом. Изменения производственных исходников, установка сервера и изменение профилей не выполнялись. Все шесть GPU после завершения имеют 15 MiB служебной памяти и 0% utilization.
