# Этап 7: диагностика DSpark для DeepSeek-V4.1

Настройка длины draft и confidence не дала устойчивого ускорения на проверенных запросах. Draft длиной 1 уменьшает потери относительно длины 3, но не обеспечивает стабильного выигрыша относительно обычной генерации. Производственные исходники, установленный сервер и рабочий профиль не менялись. Результат подготовлен для review перед коммитом.

Дата: 8 октября 2026 года. Ветка `my_build_upstream_20261007`, HEAD `11638b68545860e96b055798e995bb14be3d0e88`.

## Сборка и условия сравнения

Использован сохранённый CUDA Release snapshot этапа 5 `stage5/candidate-bin`. Его встроенная версия `b11012-cc7bfba3b` относится к базе до коммита этапа 5; фактические исходники затем закоммичены как `11638b685`. Перед каждым запуском проверены hashes бинарников, пути и hashes восьми загруженных llama/ggml/mtmd библиотек. Отдельное незакоммиченное исправление reasoning-budget для Continue в snapshot не входит; соответствующие исходники сохранены без изменений.

Шесть GPU закреплены UUID: пять RTX 4090/4090 D по 49140 MiB и RTX 3090 24576 MiB, драйвер 580.159.04. Автоматический fit отключён, target использует layer split `1,1,1,1,1,0.4`, размещение 8/8/7/8/7/2 слоя, output на последнем GPU. Это фиксированное размещение отличается от исторических запусков с автоматическим fit, поэтому текущие скорости сравниваются внутри этой серии. Context 8192, batch 2048, ubatch 512, один slot, target/draft KV F16, 12 CPU threads. В основном benchmark verbosity 3; дополнительные контрольные запуски с verbosity 4 сохранили размеры model/compute buffers.

Проверены шесть конфигураций: DSpark выключен; draft длиной 1/2/3 с `p_min=0`; длиной 3 с порогами 0,3 и 0,6. Для каждого варианта сервер перезапускается: HTTP overrides speculative-параметров в этой ветке отключены, а размер draft-графа определяется CLI. Порог confidence применяется после вычисления всего draft-блока и может уменьшать ширину проверки target, но не стоимость уже построенного draft.

На конфигурацию выполнены два исходных диагностических запроса по 128 токенов, четыре warmup и три серии измерений на четырёх prompt с лимитом 256 токенов, всего 18 запросов. Порядок prompt между сериями менялся. Сохранён исходный raw prompt этапа 0 (1655 tokens для DeepSeek), добавлены HTML/SVG с пеликаном, Python merge intervals и объяснение database indexes. Три новых prompt отрендерены через `/apply-template` с отключённым thinking. Везде temperature 0, seed 1234, `cache_prompt=false`, полный массив выходных token IDs; естественный EOS не подавлялся.

## Совместимость target и draft

Target: десять частей `DeepSeek-V4.1-Flash-Protected-Q2_K-Q8_0_Engram-imatrix`, архитектура `deepseek41`, 40 слоёв, hidden size 5120, словарь 129280. Модель имеет смешанную точность: Q2_K/Q3_K для части экспертов, Q5_K/Q6_K/Q8_0/BF16/F32 для остальных тензоров; большие Engram-таблицы Q8_0 читаются лениво на CPU. Название Q2_K не означает, что все веса имеют одну точность.

Draft: `DeepSeek-V4.1-Flash-DSpark-MXFP4.gguf`, 7,43 GiB, архитектура `dflash`, три слоя, hidden size 5120, `dsv41_semantics=true`, `block_size=5`, target layers 37/38/39. Девять крупных MoE-тензоров имеют тип MXFP4; attention/projection преимущественно Q8_0, norms F32, Markov и confidence BF16. Размеры `fc`, Markov heads и `conf_proj` согласованы с target и словарём.

Массивы tokens/token_type/merges, их SHA256, tokenizer pre/model и специальные BOS/EOS/PAD совпадают. Draft дополнительно объявляет mask token 128799; в target этот metadata key отсутствует, но словарь тот же. Точный revision исходного checkpoint в metadata не указан: подтверждена структурная совместимость, а не тождество обучающих ревизий.

Локальные Q8_0/MXFP4 drafts для V4-0731 имеют hidden size 4096 и target layers 41/42/43. Для V4.1 с 40 слоями они несовместимы и не использовались. Совместимого V4.1 draft другой точности не найдено. Влияние квантования отдельно не измерено; низкая acceptance сама по себе не доказывает, что причина в MXFP4 или квантовании target.

Все 108 запросов завершились успешно, серверы вышли с кодом 0. Внутри каждого варианта три измеренных ответа на каждый prompt совпали по token IDs и тексту. Warmup исключён из таблицы; указана медиана decode в токенах/с.

| Draft 1, p=0 | 46,78 | 47,92 | 47,97 | 44,74 |

Для исходного prompt обычный режим выдаёт 256 токенов до лимита, DSpark заканчивает на 122/107/120 токенах. Показатель 46,78 против 45,67 у draft 1 относится к разным ответам и длинам и не является доказанным ускорением одинаковой работы. На трёх новых prompt длина везде 256, но ответы также преимущественно различаются. Исключение: Python с p=0,3 совпал с native во всех повторах, при этом медленнее на 11,2%. Полнота HTML, качество кода и смысловая эквивалентность ответов не оценивались: это замеры выходных префиксов.

Draft 1 относительно native: около -0,3% на SVG, -0,4% на Python и -7,5% на indexes. Draft 3 с p=0: -5,9%/-11,1%/-22,3% на тех же трёх prompt. Увеличение порога до 0,6 не улучшило скорость.

Пик суммарного использования VRAM по одновременным секундным samples: 196,72 GiB без DSpark и 206,14–206,72 GiB с ним. Измерения памяти относятся к короткому контексту и одному slot.

## Greedy off/on

Диагностические ответы с `n_predict=128` расходятся с индекса 33 (34-го токена) для draft 1/3 и с индекса 17 для draft 2. Token IDs и первые отличия сохранены. На позиции 33 native выбирает `23914` (` entries`), DSpark — `72888` (` checkpoint`); native logprob gap этих двух вариантов всего 0,00435. Возвращаемый logprob 0 для принятого draft-токена является условным значением API, а не измеренной уверенностью target.

Контроль `--spec-verify-policy fixed --spec-verify-k 0` сохранил все 128 native token IDs в обоих повторах. При этом draft-граф, извлечение слоёв target и передача признаков включены, но draft-токены не попадают в target batch. Это исключает само включение capture/injection как достаточную причину расхождения в данном запросе.

В target-only replay принудительно поданы первые 64 native output tokens и сохранены 65 полных logit rows на каждый из десяти вариантов context. Draft-модель не загружается, откатов нет. Итоговый harness использует серверные `swa_full=false` и prefill 1139/512/4; native single-token argmax совпал с сервером во всех 65 строках. Контроль output capacity 1 против 4, включение capture и резерв `n_rs_seq=1/3` при width=1 сохраняют logits побитно.

| Decode width | Отличия argmax от native на общем префиксе, индексы | Logit(` entries`) минус logit(` checkpoint`) на индексе 33 |
| --- | --- | ---: |
| 1 | нет | +0,00434875 |
| 2 | 33, 59 | -0,27079201 |
| 4 | 33 | -0,08318710 |

При width=2 capture + reserve 1 побитно совпали с plain width=2; при width=4 capture и reserve 3 тоже не меняют logits относительно plain width=4. Таким образом, изменение ширины вычисления target само по себе воспроизводит выбор ` checkpoint` на 34-м токене, даже без draft и rollback. Это подтверждённая причина, достаточная для исходного off/on расхождения в проверенном сценарии. Width=3, соответствующий draft 2, в replay не проверялся.

Максимальная абсолютная разница logits относительно width=1 составляет 4,428 для width=2 и 4,113 для width=4; RMS по всем 65 строкам около 0,211. Поэтому результат не объявляется безобидной погрешностью округления. Конкретная операция или CUDA kernel, создающие расхождение, не локализованы; строгая совместимость batch paths не исправлена. Два предварительных replay с несогласованными defaults не прошли native-контроль и исключены из вывода о сервере; сохранены отдельно с пометкой excluded.

## Профиль затрат

Профиль снят отдельно от benchmark: `LLAMA_DSPARK_PROFILE=1`, draft 3, p=0. Nsight Systems 2025.3.2 записал CUDA/NVTX только вокруг второго диагностического запроса после прогрева; третий запрос выполнен после остановки CUDA capture. Ни синхронизации stage timers, ни node-level trace не входят в основную таблицу скоростей.

Третий запрос: 120 выходных токенов, decode 2848 мс; 66 проверок target шириной 4, всего 198 draft/53 accepted. Средняя прибавка 0,803 draft-токена, то есть примерно 1,803 нового токена за шаг после первого токена prefill.

| Измеренный участок | Суммарно, мс | Медиана на шаг, мс |
| --- | ---: | ---: |
| Draft graph + synchronize | 357,71 | 5,419 |
| Target verify + synchronize | 2404,98 | 36,225 |
| Target sampling | 18,98 | 0,302 |
| Select | 4,48 | — |
| Checkpoint bookkeeping | 0,36 | 0,005 |
| Cleanup / scheduling partial rollback | 1,04 | 0,015 |

Основная статья — проверка target, около 84,4% server decode time; draft graph занимает около 12,6%. Часть передачи/инъекции и обслуживания очереди находится вне этих именованных участков или завершается при последующей синхронизации. Это не полный неперекрывающийся профиль каждого kernel.

Target использует `n_rs_seq=3` и bounded partial removal. Полного checkpoint restore/replay в этих запросах нет. Отброшено 145 непрошедших draft-токенов; `cleanup` измеряет постановку partial rollback, а GPU-восстановление compressed state входит в последующие вычисления target. Отсутствие отдельного события `stage=rollback` не означает нулевую стоимость отката.

В CUDA trace подтверждены 295543 kernel events и 18408 copy events за интервал 5,452 с, включающий prefill и decode. 4038 вызовов `cudaMemcpyPeerAsync` соответствуют паре DtoH/HtoD активностей на каждый вызов: 2,13 GiB в каждом направлении, суммарное device time 372,93 мс. Обычные host copies дополнительно дают около 428,85 мс суммарной активности. Эти времена могут перекрываться; их нельзя складывать как задержку запроса. Trace включает обычную работу target на шести GPU и DSpark, без native trace-контроля нельзя приписывать весь обмен исключительно DSpark.

Наблюдаемая причина отсутствия выигрыша: target проверяет блоки из четырёх токенов, принимая в среднем меньше одного draft-токена, а построение draft и обмен добавляют затраты. Пороги отбрасывают часть предложений после вычисления draft и не устраняют эту цену. Полный rollback через сохранение/загрузку checkpoint не является причиной потерь в проверенной серии.

## Решение и ограничения

Для проверенной модели и текущих GPU разумный основной вариант — генерация без DSpark. Если DSpark нужен для отдельного эксперимента, из проверенных настроек draft 1 с p=0 даёт наименьшие потери; гарантировать ускорение или одинаковый greedy-ответ нельзя. Рабочие настройки пользователя автоматически не менялись.

Отдельно остаются получение совместимого V4.1 draft другой точности, проверка обучающей ревизии и строгого совпадения target logits при разных размерах batch. Другие контексты, несколько slots, thinking и sampling не проверялись. Историческое расхождение DeepSeek после save/restore этапа 3 этим экспериментом не исправлено и не объявляется той же проблемой.
