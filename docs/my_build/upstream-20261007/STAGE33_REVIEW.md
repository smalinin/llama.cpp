# Этап 33: завершение работы над DeepSeek DSpark

Ветка `my_build`, исходный HEAD `135c2110f`. Review принят пользователем; пункт DSpark закрыт. Установленный сервер и профили не заменены.

## Решение

**Расхождения target-вычислений исправлены в производственном графе, без диагностических callbacks. Ускорения с проверенным MXFP4 sidecar нет: для этой конфигурации рекомендован DSpark off.** Это итог текущей работы, а не предложение следующего этапа диагностики.

Обычная генерация сохранила проверенные ответы и скорость. DSpark N=1/N=3 теперь выдаёт те же greedy ответы. Однако согласование арифметики увеличивает стоимость проверки draft; даже после прогрева N=1 уступает native на 5-19%, N=3 на 25-43% в проверенных случаях. Универсальная невозможность ускорить DSpark из этого не следует; практическая польза именно этой связки не подтверждается.

## Причины и код

Ширина verification меняла арифметику floating-проекций и routed MoE, а также форму FlashAttention. После этапа 32 raw KV уже упорядочивался логически, но для нескольких запросов собиралось объединение их окон. Оно отличается от отдельного окна каждого запроса. Кроме того, размер дополнения compressed KV зависел от последнего запроса батча.

В `llama-graph.cpp/.h`, `models/deepseek4.cpp` и `models/deepseek41.cpp`:

- Короткий однопоследовательный decode/verification определяется по всем запрошенным outputs и ширине не больше `n_rs_seq + 1`.
- Floating F32/F16/BF16 проекции используют FP32 и отдельные query-колонки, включая HC, router, compressor, indexer и группированную wo_a. Routed MoE строится существующим single-query путём для каждой колонки.
- Каждый query attention получает собственное логическое raw SWA окно и собственный padded compressed extent. Учтены оба плана сжатия, используемые настоящим V4.1; graph reuse проверяет размеры.
- Большие prefill-батчи и другие архитектуры сохраняют обычный batched путь. Формат state и исправленный хвостовой rollback сохраняются.

Используются существующие CUDA операции в обычном графе. Результат не пересчитывается через callback и не подменяется после выполнения. Новых специализированных CUDA ядер или новых флагов запуска нет.

Fixed-history replay охватывает queries 6617-7640, включая прежние проблемные позиции. Он сравнивает каждый элемент logits, а не только выбранный argmax. Свободные серверные запросы отдельно проверяют настоящие draft proposals и их откаты. В финальных проверках включены обычные CUDA Graphs, evaluation callback отсутствует.

## Скорость на одинаковых ответах

Токены/с по серверным `predicted_per_second`. Для четырёх коротких запросов указано второе выполнение после прогрева графов; первые выполнения также сохранены. Длинные fresh/cache измерены по одному разу. Это последовательные локальные замеры, без заявления статистической гарантии для любых запросов.

| Сценарий | Off | N=1 | N=3 |
| --- | ---: | ---: | ---: |
| Baseline | 45.12 | 42.51 (-5.8%) | 33.84 (-25.0%) |
| HTML/SVG | 46.80 | 42.52 (-9.1%) | 32.14 (-31.3%) |
| Python | 46.82 | 40.36 (-13.8%) | 29.03 (-38.0%) |
| Объяснение | 46.78 | 38.03 (-18.7%) | 26.67 (-43.0%) |
| Длинный fresh | 36.26 | 33.98 (-6.3%) | 26.64 (-26.5%) |
| Длинный cache | 39.65 | 37.80 (-4.7%) | 29.89 (-24.6%) |

На коротких запросах принимается 33-56% предложенных draft-токенов N1 и 16-32% N3. Стоимость проверки и draft не окупается. DSpark добавляет около 9,5 GiB занятой VRAM после выполнения запросов. N1 уменьшает потери относительно N3, но в проверенных случаях всё равно уступает native. Рабочие настройки автоматически не менялись.

По сравнению с прежним некорректным batched DSpark исправленная проверка дороже. Это не регрессия обычной генерации: её результаты сохранены. Нет оснований устанавливать этот вариант ради ускорения; фикс нужен для согласованного поведения speculative decode.

## Границы и артефакты

Реальная модель: `DeepSeek-V4.1-Flash-Protected-Q2_K-Q8_0_Engram-imatrix`, оригинальный `DSpark-MXFP4`, шесть GPU, F16 KV, context 8192, batch 2048/ubatch 512, один слот. Q8 KV проверен на малой модели. Воспроизводимость произвольного sampling, multi-slot verification и 128K этим результатом не заявляется. Качество модели относительно исходных весов не оценивалось.

Промежуточные неудачи сохранены отдельно: первый кандидат не заполнил размеры второго плана сжатия, а первая смешанная фикстура имела несовместимую маску candidate reuse. Оба случая исправлены до финальных проверок и не включены в положительный результат. Дополнение группированной floating-проекции убрало остаточные численные отличия малой CUDA-модели.
