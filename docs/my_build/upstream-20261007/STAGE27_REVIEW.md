# Этап 27. Узкий хвостовой rollback DeepSeek-V4.1

По отдельному поручению пользователя после закрытия этапов 0-26 реализован фикс выбора следующей raw SWA ячейки при удалении хвоста. Review принят пользователем; фикс и результаты включены в коммит этапа27. Установленный сервер и профили не заменены.

## Изменение

В `llama_kv_cache::seq_rm` для DeepSeek-V4.1, SWA и отдельного потока на последовательность начало поиска возвращается к освобождённой ячейке с наименьшей логической позицией. Условие действует только для удаления до конца последовательности с сохранённым префиксом. Полная очистка, удаление ограниченного диапазона, wildcard, общий поток нескольких последовательностей, другие архитектуры и compressed KV сохраняют прежнюю политику.

Пример: verification записывает четыре позиции в ячейки `[765,766,767,0]`, принимается первая, остальные удаляются. Прежний обход по физическому индексу выбирал ячейку 0. Новый код выбирает 766, поэтому повторное декодирование продолжает то же физическое размещение, что и scalar. Это исправление воспроизводимости размещения; доступ к ячейке 0 сам по себе не был недопустимым обращением к памяти.

Производственный diff: один файл, `src/llama-kv-cache.cpp`, +8/-2 строки. CUDA-арифметика, формат состояния, API и настройки не менялись. Пересобран один объект KV и перелинкована отдельная `libllama`; остальные объекты и библиотеки проверены по SHA. Основной build и установленный `/home/sergei/_llama_cpp/my_build/llama-server` не заменены.

На прежних первых численных границах query6910/7251 используется ячейка 766 вместо 0; max/RMS разности logits теперь 0/0. На прежних точках смены токена query7020/7401 также полное побитовое совпадение; выбираются правильные native ID 35865 и 4.

Две свободные N3 генерации, fresh и cached, совпали со своими native эталонами по всем 1024 токенам, тексту ответа и stop-полям. В прежнем N3 первые отличия были на output404/785 (405-й/786-й токен); теперь их нет. Prompt содержит 6617 токенов; fresh cache_n=0, cached cache_n=6613 с повторным prefill четырёх токенов. Для wide generation indexer counts равны 8*width; в prefill и заключительном scalar width1 вмешательств indexer нет.

Использованы прежние шесть GPU, один слот, context8192, batch2048/ubatch512, F16 KV, CUDA graphs выключены; N3, temperature0, ignore_eos=true. Все GPU-запуски последовательны. Всего выполнены 27 allocator cases на двух библиотеках, шесть model replay и ровно два HTTP completion. Более широкая матрица предыдущих этапов повторно не запускалась.

## Что именно подтверждают результаты

Model replay и свободная N3 проверка используют прежний диагностический callback этапа24. Его header и raw-layout header побайтно сохранены; арифметические исправления из диагностики не перенесены в production. В replay удалена проверка совпадения с прежним ошибочным размещением (см. `replay.patch`); вместо неё анализатор требует совпадения с scalar. Проверки согласованности raw-plan до/после decode сохранены. Входные токены, ширины, позиции и вызовы rollback взяты без изменений из этапа26. Cached replay сначала исполняет полное записанное fresh расписание, затем partial restore.

Сравнение полных logits ограничено правильным префиксом записанного расписания. Его дальнейшие токены происходят из старой расходящейся генерации и не служат эталоном native. Четыре отдельные SHA-проверки покрывают полные контрольные histories.

Фикс устраняет установленный сдвиг размещения при хвостовом rollback. Он не устанавливает конкретную CUDA-операцию, которая превращала смену physical layout в численную разницу, и не доказывает общую побитовую совместимость обычного production DSpark N3. Встроенный callback дублирует штатные операции, поэтому время этих запусков не является замером ускорения.

Native fresh/cache расхождение query6796 и прежнее расхождение после session restore остаются открытыми. Произвольные cache states, модельное multi-slot исполнение и production throughput в этот узкий этап не входят. Весь прежний цикл тестирования не возобновлялся.
