## Flash Attention на одинаковых входах

Использован узкий capture слоя 2 с первого scalar decode этапа 9: Q F32 [512,64], K/V F16 [512,1792], маска F16 [1792], sinks F32 [64]. В каждую колонку широкого batch записаны одинаковые Q и маска; K/V/sinks общие. Запрошена та же `GGML_PREC_F32` и тот же scale. Выход scalar replay на Ada побайтно воспроизводит сохранённый выход настоящей модели.

| Ширина | Ada: max разница против своего scalar | Ampere: max разница против своего scalar |
| --- | ---: | ---: |
| 2 | 2,38419e-7 | 1,19209e-7 |
| 3/4 | 2,75392e-5 | 1,24902e-4 |
| 5/8 | 3,96341e-4 | 6,43015e-4 |
| 16 | 6,40631e-4 | 6,31690e-4 |

Все одинаковые query-колонки внутри варианта совпали; повторные вычисления стабильны. Независимый повтор с очищенным окружением и выключенными CUDA Graphs сохранил все выходные байты обеих архитектур. Scalar Ada и Ampere также различаются (max 6,04033e-4).

Это устанавливает зависимость арифметики от batch/архитектуры на фиксированных входах. В `fattn-mma-f16.cuh` используются half Q/scale и probability tiles, а конфигурация блоков/reduction меняется с шириной. CPU double reference с отдельным контролем округления Q не эмулирует весь CUDA online softmax. Ошибка против него не доказывает нарушение precision-контракта, и одна ширина не оказывается во всех метриках точнее другой. Новый CUDA correctness bug этим тестом не установлен.

Источники: [attention replay](stage10/attention-replay.cpp), [входы и происхождение](stage10/attention-input-manifest.json), [результаты](stage10/attention-replay-summary.json), [CPU reference comparison](stage10/attention-reference-summary.json).

## Подмена attention внутри полного replay

Диагностический callback после prefill пересчитывает каждый широкий Flash Attention по одной query, используя текущие Q/K/V/mask/sinks. Полученный scalar-выход подставляется перед следующими операциями. Источники вложенного графа отделены от операций родительского графа; проверяется ограничение до трёх узлов. Batch остальных операций и обновления KV остаются прежними. Это диагностическая интервенция, а не предлагаемый производственный режим.

| Режим | Width 2: max/RMS разницы logits против width 1 | Width 4: max/RMS | Индексы разных argmax, с 0, width 2 / 4 |
| --- | --- | --- | --- |
| Baseline с контрольной синхронизацией | 5,284104 / 0,244460 | 7,098978 / 0,279226 | нет / 19 |
| FP32 float MUL_MAT только после prefill | 5,041233 / 0,229195 | 7,090881 / 0,304767 | нет / нет |
| Только scalar attention | 3,808814 / 0,234071 | 5,016908 / 0,229386 | 19 / нет |
| FP32 float MUL_MAT и scalar attention | 3,547752 / 0,212877 | 2,142161 / 0,193741 | 19 / нет |

Все четыре scalar-контроля воспроизводят native SHA и все 65 native token IDs. Шесть baseline/FP32 контрольных SHA совпали с этапом 9. Уменьшение max/RMS не гарантирует одинакового greedy выбора: для сочетания FP32/scalar attention width 2 gap `verify - check` на индексе 19 равен -0,125444 против +0,294163 у scalar. Совпадение width 4 на 65 строках также не закрывает свободную генерацию.

Подмена attention не устраняет остаточное расхождение и не пригодна как самостоятельное исправление. Производительность этого диагностического режима не измерялась; его время не сравнивается с HTTP throughput.

Источник: [summary полного replay](stage10/target-attention-output/summary.json), [harness](stage10/target-attention-controls.cpp).

## Где усиливается остаточная разница

Сняты данные первого decode-вызова для режима FP32 float MUL_MAT плюс scalar attention. Варианты с capture только FA, с границами слоёв 2/3 и с Q_B-проекцией сохраняют полные SHA всех 65 logits-векторов для widths 1/2/4.

На слое 2 первые query, все видимые K/V, маски и sinks совпадают побайтно. Видимы те же 956 строк из физического буфера длиной 1792; после scalar-подмены FA-выход и `attn_out-2` также совпадают. Затем малая разница остаточного HC/FFN-пути растёт:

| Граница, первый токен, width 2 против scalar | Max разница |
| --- | ---: |
| `hc_attn_post-2` | 1,78814e-7 |
| `ffn_norm-2` | 1,34110e-7 |
| `ffn_out-2` | 2,49594e-5 |
| `attn_norm-3` | 3,56697e-6 |
| Нормализованный выход Q_A слоя 3 | 1,67149e-3 |
| Линейный выход Q_B до RoPE | 1,74870e-2 |
| Q после RoPE | 1,90553e-2 |
| `attn_out-3` | 1,22294e-2 |

Для width 4 наблюдается почти та же цепочка. На слое 3 маска и список видимых позиций сохраняются, меняется только текущая raw-KV строка 119 (max 4,88281e-4); новая сжатая строка и остальные видимые строки совпадают. На проверенных слоях/шаге нет дополнительной доступной будущей позиции. Это не доказательство причинности всей модели и всех rollback-сценариев.

## Изолированные Q6_K Q_A/Q_B и Q8_1 активации

Для слоя 3 сохранены реальные Q_A [5120,1280] и Q_B [1280,32768], обе Q6_K, и входы первого токена при widths 1/2/4. Q_B взят из GPU capture; Q_A и его RMS-weight извлечены из GGUF с записанными offset/SHA256. Q_A replay включает исходную RMS-нормализацию с epsilon 1e-20 и исходный normalization weight.

Для каждого из трёх входов независимо повторены widths 1/2/4, с оригинальными Q6_K-весами и с их деквантованной F32-копией, на Ada и Ampere. На неизменном входе обе Q6_K-проекции дают **побайтно одинаковый выход** для всех ширин и архитектур. Выходы Q_A/RMS и Q_B из модели воспроизведены точно во всех 12 соответствующих проверках. При F32-весах остаются небольшие различия порядка 1e-6 между ядрами; это отдельный контроль арифметики.

При разных фактических входах scalar и width 2:

| Операция | Max разница входов | Max разница выходов Q6_K | Max разница с теми же весами, деквантованными в F32 |
| --- | ---: | ---: | ---: |
| Q_A + исходная RMS | 3,56697e-6 | 1,67149e-3 | 9,28640e-5 |
| Q_B | 1,67149e-3 | 1,74870e-2 | 5,64885e-3 |

F32-веса взяты из **того же квантованного файла**, исходный checkpoint большей точности не используется. Этот контроль убирает промежуточное Q8_1-квантование входа MMVQ, не восстанавливая информацию, уже потерянную в Q6_K-весах.

CPU double reference с эмуляцией Q8_1 (32 значения, integer rounding и half scale) воспроизводит captured Q_A/RMS с max error до 9,53674e-7, Q_B до 1,90735e-6. Модель Q8_1-округления показывает изменение девяти integer-компонент и трёх half-scale блоков на Q_A, затем 21 компоненты и пяти scale блоков на Q_B. Это CPU-модель уравнений CUDA, не прямой capture GPU integer-буфера; её точность отдельно проверена по результату проекции.

Таким образом, для этих двух операций большая разница вызвана изменением входа и чувствительностью квантованного вычисления, а не расхождением batch-ядер на одинаковом входе. Источник самых ранних небольших отличий HC/FFN не устранён; весь остаток logits одной этой цепочкой не объявляется объяснённым.

Источники: [projection summary](stage10/projection-summary.json), [Q8 rounding](stage10/q8-input-rounding.json), [CPU reference](stage10/projection-q8-reference.cpp), [Q_A extraction](stage10/projection-qa-inputs/blk.3.attn_q_a.weight-extraction.json).

## Воспроизведение и ограничения

[build-commands.json](stage10/build-commands.json) содержит команды пересборки. Запуски и подготовка данных сохранены в `run-*.py`, `prepare-*.py`, `extract-qa-weights.py`; анализ в `analyze-*.py`. Скрипты используют прежние локальные артефакты этапов 5/7/8/9, включая неизменяемые библиотеки и CPU metric/reference libraries. Пути в manifests указывают на локальную папку, большие входы/выходы в Git не включены. Для повторного запуска нужно сохранить старые output-каталоги под другими именами или использовать новую соседнюю папку артефактов; инструменты отказываются перезаписывать результаты.

Первая полная попытка прервана при подготовке scalar-интервенции для исправления изоляции источников вложенного графа; её результаты исключены и сохранены отдельно. Проба CPU reference с совпавшим именем бинарника и выходной папки также исключена, затем успешно повторена в отдельной папке. GPU-процессов после проверок нет.

Следующий шаг: изолировать начальное отличие FFN слоя 2 на одинаковых входах с сохранением fusion, expert IDs и весов, затем оценить подход к точности промежуточных активаций с замерами стоимости. Одного повышения точности BF16/HC либо изменения attention недостаточно. Флаги из диагностики не переносились в рабочий граф. Исправление полной совместимости нужно подтвердить свободными greedy off/on генерациями на нескольких prompt; нового HTTP/performance сравнения на этом этапе нет, ускорение DSpark остаётся неподтверждённым.
