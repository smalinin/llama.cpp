# Этап 3: сохранение и восстановление состояния

Этап 2 принят пользователем и закоммичен: `c788620d19a365fd50f53add6166bbc0dc61fbc1`. Изменения этапа 3 подготовлены поверх него в ветке `my_build_upstream_20261007`. Review этапа 3 принят пользователем; коммит `0a1ad5457170f3f99318e89b2e36d40fd4cc1685`. По указанию пользователя начат этап 4.

## Изменения

Адаптированы два upstream-патча:

- [#27530](https://github.com/ggml-org/llama.cpp/pull/27530), `08618ff8e735141d8e4e5be28e6d6af170e4757b`: после неудачного восстановления очищаются данные затронутых KV/recurrent-строк. Отложенные tensor writes в host/device reader отбрасываются, чтобы destructor не записал повреждённые данные обратно после очистки.
- [#28498](https://github.com/ggml-org/llama.cpp/pull/28498), `210791069bf5460bef3c09b982ee6f0aa9967404`: точные размеры K/V rotation сохраняются в state payload и проверяются перед чтением тензоров. Расчёт rotation сохранён эквивалентным локальному, включая indexer guards GLM-DSA/DeepSeek-V4.1 и пустые MTP caches.

Оба патча конфликтовали с локальными реализациями. Очистка адаптирована к hybrid/indexer caches, SWA, DSA/MSA и compressor state DeepSeek-V4.1. При восстановлении отдельной последовательности сохраняются другие последовательности, включая совместно используемые ячейки. Очистка следует фактическому размещению записанных строк и учитывает transposed V. PARTIAL_ONLY сохраняет компоненты, которые этот режим не восстанавливает: base attention, индексатор и compressed K. У shared MTP KV сохранён guard, исключающий очистку памяти основной модели.

При проверке реального GLM5NEXT-слота обнаружена дополнительная существующая ошибка: файл, оборванный на последнем байте, доходил до assert вместо возврата ошибки. POSIX reader читает оставшуюся часть файла, поэтому добавлена проверка границ именно в state-file reader и минимального заголовка в load API. Общий reader GGUF/direct I/O не менялся. Регрессия добавлена в существующий `tests/test-save-load-state.cpp`, вместе с upstream проверками failed restore и rotation. Новых файлов в `tests/*` нет.

Исходники и существующий тест: 20 файлов, 808 вставок и 165 удалений. SHA256 проверенного source.patch: `f937120edee834bf1948f9991100c4d85e74452f91829d3a4cbe4e25c4ebe20f`.

## Проверки

- CUDA Release сборка затронутых инструментов и тестов прошла.
- Профильные существующие CTest: **9/9**, включая генерацию fixtures, batch allocation, recurrent rollback, save/load state для 113 dummy architectures, Qwen4Exp Q8 KV и fragmented state restore. Финальная серия включает случай обрыва последнего байта файла.
- `state-fault.cpp`: **108** сценариев прошли на CPU, CUDA sm89 (GPU4) и sm86 (GPU3). Пять fixture-архитектур: Llama, GLM5NEXT, Qwen4Exp, GLM-DSA, DeepSeek-V4.1; unified/separate KV, F16 без flash и Q8_0 с flash, отказ в середине/конце tensor writes. После записи NaN-байтов проверяются нули в фактически затронутых диапазонах, побайтовая сохранность другой последовательности, конечные logits и NMSE <= 1e-5 относительно чистого decode. Шесть Q8_0 контекстов для маленькой DeepSeek fixture не поддерживаются: размер головы 8 меньше блока Q8_0 32. Два варианта отказа для каждого из них не запускались и не посчитаны успешными.
- Старые библиотеки этапа 2 воспроизводят stale tensor data (`cache_k_l0`, offset 0, size 8192), код 1. Новая библиотека проходит этот сценарий в матрице.
- `state-api.cpp`: **60/60**, host/device, flags 0/1/2/3, unified/separate, успешный побайтовый roundtrip, сохранность другой последовательности после отказа и PARTIAL_ONLY. Обрыв полного state проверяется в двух местах. Ранний отказ в заголовке DeepSeek до изменения памяти сохраняет прежние последовательности; отказ после начала восстановления очищает затронутое состояние.
- Rotation regression: старая библиотека принимает state с несовместимым K rotation и проваливает тест; новая возвращает 0. Если конкретная архитектура/тип KV не меняет rotation при переключении режима, её успешный restore проверяется отдельно; отсутствие изменения rotation не считается проверкой rejection.
- `file-truncated.cpp`: старая библиотека прерывается (134), новая отклоняет обрыв последнего байта, очищает последовательность и успешно выполняет следующий decode.

Подробные результаты: [test-results.json](stage3/test-results.json). Команды и harnesses: [stage3/README.md](stage3/README.md), [reproduce-harness.sh](stage3/reproduce-harness.sh).

## Совместимость состояния

| Формат | До | После | Совместимость |
| --- | --- | --- | --- |
| Session file | 10 | 11 | Старые файлы отклоняются |
| Sequence/slot file | 3 | 4 | Старые файлы отклоняются |
| Raw state buffers | Без внешней версии | Добавлены размеры rotation | Прежний непустой KV payload несовместим |

Для Llama F16/Q8_0 проверены четыре варианта: session, sequence, full raw и sequence raw. Новая библиотека отклонила **8/8** старых состояний; старая отклонила **8/8** новых; новая приняла **8/8** новых. Восстановление state из другого rotation режима отклоняется даже при совпадающей версии файла.

Сохранённые prompt/session/slot caches потребуется создать заново; автоматической миграции нет. GGUF моделей и настройки квантования не меняются. Результат этой проверки относится к сериализованным непустым KV состояниям, а не к обещанию универсальной идентификации произвольного raw buffer или всех свойств модели: существующая проверка model info остаётся ограниченной архитектурой.

## Реальные модели

Пять on профилей (четыре F16 и дополнительный Qwen Q8_0) прошли по семь запросов: четыре стандартных, после успешного restore и после двух отказов. На всех профилях успешный save/erase/restore/resave даёт побайтовое совпадение state-файла; truncate последнего байта и подмена версии на 3 возвращают HTTP 400, после них работает новый greedy запрос.

| Профиль | Ответы до/после этапа 3 | Побайтовый roundtrip | Размер state | Truncate / старая версия |
| --- | --- | --- | --- | --- |
| GLM5NEXT | 4/4 | Да | 174.34 МиБ | 400 / 400 |
| Qwen4Exp | 4/4 | Да | 169.63 МиБ | 400 / 400 |
| GLM-5.3 / GLM-DSA | 4/4 | Да | 161.98 МиБ | 400 / 400 |
| DeepSeek-V4.1 / DSpark | 4/4 | Да | 13.63 МиБ | 400 / 400 |
| Qwen4Exp Q8_0 KV | Отдельный режим | Да | 142.61 МиБ | 400 / 400 |

Для четырёх исходных F16 профилей **16/16** стандартных ответов совпали с этапом 2 по token IDs и тексту, совпали также все draft/accepted. GLM5NEXT использовал фиксированное размещение из контрольной серии этапа 2, остальные профили - прежний fit on. Q8 режим не имеет старого real-model baseline: он проверяет работоспособность квантованного KV, а не эквивалентность разных точностей. Ответы Qwen F16/Q8 различаются и в greedy, и в sampling; сравнение разных KV точностей не используется как проверка регрессии исходников. Эти короткие серии не являются замером ускорения.

Запросы после отказов и обычного restore совпали с исходным greedy Qwen, GLM-DSA и DeepSeek. У GLM5NEXT они совпадают с одним из двух greedy повторов; сами повторы расходятся в обеих версиях с token index 58. В on запросах после restore `cache_n=0`, поэтому этот результат отдельно от проверки продолжения из сохранённого KV.

Native target continuation (MTP/DSpark off) прошёл для GLM5NEXT, Qwen F16/Q8_0 и GLM-DSA: использован весь сохранённый префикс, обработан один новый токен, 32/32 выходных токена и текст совпали. DeepSeek-V4.1 использует сохранённый префикс, но продолжение меняется со второго выходного токена.

| Профиль | Cached tokens до / после restore | Новые входные токены до / после | Совпавшие выходные токены |
| --- | --- | --- | --- |
| GLM5NEXT | 1687 / 1687 | 1 / 1 | 32/32 |
| Qwen4Exp | 2064 / 2064 | 1 / 1 | 32/32 |
| GLM-5.3 / GLM-DSA | 1687 / 1687 | 1 / 1 | 32/32 |
| DeepSeek-V4.1 | 1686 / 1686 | 1 / 1 | Расхождение со второго токена |
| Qwen4Exp Q8_0 KV | 2064 / 2064 | 1 / 1 | 32/32 |

Дополнительный Qwen Q8 MTP on контроль: до erase использовано 2160 cached tokens, после restore - 0 (полный prefill 2161 токена); 32 выходных токена совпали. Он подтверждает работу fallback, но не восстановление draft state. Всего в финальных real-model сериях выполнено **52 completion запроса с HTTP 200**: 35 стандартных/state в пяти on профилях, 2 дополнительных Q8 MTP продолжения и 15 native target запросов. Сравнение продолжения DeepSeek не прошло, несмотря на HTTP 200. Native off серии служат проверкой состояния; полного четырёхзапросного off benchmark на данном этапе нет.

**Ограничение DeepSeek-V4.1:** на сохранённых библиотеках этапа 2 native save/erase/restore меняет продолжение точно так же: cache_n 1686, prompt_n 1, первое расхождение - index 1. Исходный 32-токенный ответ, контрольное продолжение и продолжение после restore побайтово совпали между старой и новой версиями по token IDs и тексту. Это существующая ошибка, не устранённая данными upstream backports. Критерий сохранения поведения реального DeepSeek native continuation **не закрыт**; отдельная диагностика/исправление остаются открытыми. Побайтовый roundtrip сериализованного payload и отсутствие падения сами по себе её не исключают. Полная причина расхождения пока не определена. Доказательство: [deep-continuation-before-after.json](stage3/deep-continuation-before-after.json). Отдельный старый контроль добавляет 3 completion запроса сверх итоговых 52.

Результаты: [real-comparison.json](stage3/real-comparison.json), [real-verification.json](stage3/real-verification.json). Контроль продолжения отдельно проверен на существующей локальной TinyLlama: cache_n 12, 32/32 токена совпали.

Slot save/restore сервера сохраняет target state и token IDs, без draft/speculative state (`tools/server/server-context.cpp`, SLOT_SAVE/SLOT_RESTORE). После erase/restore запрос с MTP/DSpark может перейти в полный prefill по существующей проверке согласованности target/draft; recurrent rewind тоже может потребовать reprocessing. Поэтому `cache_prompt=true` сам по себе не доказывает использование восстановленного KV. К исходным on проверкам добавлен отдельный контроль native target continuation (MTP/DSpark off): полный префикс из token IDs, один необработанный токен, одинаковые 32-токенные продолжения до и после erase/restore и обязательный `cache_n` всего сохранённого префикса. Изменения формата slot-файла для сериализации draft/speculative state не входят в эти upstream-патчи.

## Происхождение результатов и ограничения

При запуске серверов задан LD_LIBRARY_PATH на snapshot этапа 3, реальные пути и SHA256 libllama/libllama-server-impl подтверждены через /proc/PID/maps. Все девять snapshot-бинарников совпадают с итоговой сборкой. 29 файлов моделей сверены по resolved path, размеру и mtime_ns; изменений нет. Числа проходят как проверка корректности на текущей Linux/CUDA машине, не как оценка на всех backend/platforms.

Предварительные реальные прогоны до EOF fix сохранены в `runs-pre-file-bounds` и не включаются в итоговое сравнение. Ошибочные ожидания вспомогательного harness о DeepSeek metadata/раннем отказе исправлены; финальные 60/60 получены после этого. Логи, сохранённые состояния, memory traces и бинарники остаются в workspace; в репозитории сохраняются компактные результаты и воспроизводимые scripts.

Известные ограничения этапа 2 (strict realloc диагностика, GLM5NEXT unified multi-slot pool-key assert, расхождения отдельных multi-slot ответов) этим этапом не проверены заново и не объявляются исправленными. Последние пункты плана о воспроизводимости sampling обычного GLM-5.3 и производительности DSpark остаются после всех фиксов. Этап 4 не начат.
