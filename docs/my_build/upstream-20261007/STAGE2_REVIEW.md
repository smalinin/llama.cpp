# Этап 2: порядок hidden states и резервирование recurrent-state

Исправления подготовлены в ветке `my_build_upstream_20261007` поверх `00091b7f2694f03839aec08248b11ed236619641`. Проверки завершены, результат подготовлен для review с перечисленными ниже ограничениями. Этап 2 не закоммичен.

## Изменения

Адаптированы два upstream-патча:

- [#29019](https://github.com/ggml-org/llama.cpp/pull/29019), `4453b535fd15cd5b9d5ccb956ebd38dc325c98fc`: исходные индексы токенов сохраняются в `llama_ubatch::data_t::batch_idxs`. Layer inputs и unmasked NextN переставляются по полной карте токенов; masked NextN сохраняет карту выбранных выходов logits. Чтение микробатча выполняется с нулевого смещения исходного тензора, что сохраняет совместимость с tensor split.
- [#29856](https://github.com/ggml-org/llama.cpp/pull/29856), `436f6f89e1e581249900b37a5b8a12a36a6d0912`: recurrent states собираются одной операцией `get_rows`, размер которой зависит от общего `n_rs`. Состояния текущих последовательностей и дополнительные состояния становятся views этого результата. Для специального getter, используемого Mamba, gather начинается со второй строки.

Оба upstream diff конфликтовали с локальными реализациями и адаптированы вручную. Сохранены guards пустого recurrent-cache в MTP-контекстах. В локальном пути NextN на backend также восстановлен порядок строк: masked использует перестановку выходов, unmasked - исходные индексы токенов. Для обмена строк выделена одна scratch-строка в том же backend-буфере; CUDA выполняет копии device-to-device. Getter backend-тензора синхронизирует вычисление и применяет перестановки. Уже упорядоченные строки не копируются.

Изменены шесть исходных файлов, 105 вставок и 31 удаление. SHA256 проверенного source.patch: `1ad6963b4944b652f2a64866081c11a98bc96ba6843232f3dfce6bb506eec11f`.

После reserve для `n_rs=4`, `n_seqs=4` проверяет `n_seqs=1/2/3/4` и произвольную карту состояний, обычный и специальный getter, значения основных и дополнительных состояний. Используются два CPU backend instance, чтобы allocator не выполнял молчаливый single-buffer reserve. До патча: abort `unexpected graph reallocation`, graph size 9, при `GGML_SCHED_DEBUG_REALLOC=1` и 2. После: все 8 случаев проходят даже при уровне 2.

## Ограничения строгой диагностики

Строгий CTest при `GGML_SCHED_DEBUG_REALLOC=1`: 8/9; existing rollback-тест Qwen3.5 прерывается на graph size 269. Отдельные строгие rollback-тесты Qwen4Exp и GLM5NEXT тоже прерываются (graph size 845/518). Все три падения воспроизведены с библиотекой этапа 1; после патча меняется число nodes в некоторых графах, но оставшееся падение не устранено. Обычные запуски этих тестов проходят.

Полная матрица hidden-order со строгой диагностикой прошла 156 случаев и прервалась на GLM5NEXT GPU0, graph size 316. Поэтому нельзя утверждать отсутствие перераспределений во всех графах: исправлен и изолированно проверен recurrent gather; более широкая диагностика остаётся ограничением review. Сама диагностика срабатывает до reserve и не устанавливает, будет ли увеличен физический CUDA-буфер.

CUDA row split не проверен: в этой сборке отсутствует интерфейс split buffers. Tensor split для GLM5NEXT/Qwen4Exp не поддерживается. Qwen4Exp проверен для NextN; raw layer inputs этой архитектуры содержат HC lanes, тогда как существующий capture API резервирует `n_embd` на строку. Этот отдельный вопрос размеров capture не изменён данным этапом.

## Несколько слотов и DFlash

Три слота, ubatch 64, три разных коротких prompt, greedy/seed 1234, до 64 токенов. Для каждого профиля: три serial запроса, две серии по три concurrent запроса и три cache-reuse запроса. `--no-kv-unified`: DFlash2 для GLM5NEXT, встроенный MTP GLM5NEXT и внешний MTP Qwen4Exp завершили по 12 запросов, серверы вышли с кодом 0.

DFlash с раздельным KV: до/после совпали 7/12 ответов; в обеих параллельных сериях совпали счётчики 129/177 accepted/draft (72,9%). Serial acceptance изменился с 131/172 (76,2%) на 130/176 (73,9%), reuse с 129/177 (72,9%) на 132/170 (77,6%). Каждый параллельный повтор внутри одной версии совпадает по token IDs. На старой версии reuse совпадает с предыдущей параллельной серией; после исправления во всех трёх слотах различается, хотя acceptance вырос. Полная эквивалентность ответов и выигрыш скорости на нескольких слотах не установлены: варианты выполнения и fit on влияют на результаты. Изменение захваченных hidden rows ожидается от исправления порядка, но оно не объясняет само по себе все расхождения реальной модели.

С `--kv-unified` DFlash проходит три serial запроса, затем обе версии прерываются на первой concurrent серии: `llama-kv-cache-kpool.cpp:985`, `uncached.size() <= n_update`, `incremental pool-key update capacity is too small`, SIGABRT (код сервера -6). Контроль до использовал библиотеки этапа 1, пути и хеши подтверждены manifest. Это существующая ошибка pool-key cache; проверку unified KV на реальной модели нельзя считать успешной. Соответствующие upstream k-pool изменения уже перечислены в плане для отдельного рассмотрения; они не включены в эти два патча.

MTP с раздельным KV: оба старых профиля также завершили по 12 запросов без падений. Qwen4Exp совпал до/после во всех 12 ответах. Две parallel серии в слоте 1 различаются в обеих версиях; остальные параллельные повторы и все reuse ответы совпадают. Draft/accepted совпали в 11 запросах, в reuse слота 2 изменились с 50/46 на 48/47 при том же ответе.

GLM5NEXT MTP: 9/12 ответов совпали до/после, включая все serial ответы. После исправления параллельные повторы и reuse совпали во всех трёх слотах; до исправления parallel slot 2 и reuse slots 0/1 различались. Acceptance serial не изменился (123/157), parallel1 124/158 -> 124/160, parallel2 114/157 -> 114/159, reuse 119/165 -> 114/159. Этот короткий прогон не подтверждает отсутствие любого ухудшения acceptance: отличается разбиение запросов и часть выходов. Он подтверждает работоспособность локального MTP backend-пути при нескольких слотах.

Greedy decode: off 42,52-42,57 до и 42,28-42,73 после; on 47,93-48,05 до и 47,52-48,25 после.

Исправленные серверные контроли используют `LD_LIBRARY_PATH=stage1/bin`; `/proc/PID/maps` и SHA256 фактически загруженных libllama и server-impl записаны в manifests. Ранее выполненные C++ контроли имели явную привязку к старым библиотекам и остаются действительными. Все девять бинарников текущего build совпадают с сохранёнными бинарниками этапа 2; source.patch не изменился.
