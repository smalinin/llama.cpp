# Этап 28. GLM5NEXT: падение параллельных запросов с unified KV

По поручению пользователя подготовлен фикс pool-key cache GLM-5.3-Flash (GLM5NEXT). Исходная версия - коммит `31aa1e266`, включая исправление rollback DeepSeek этапа 27. Остановка для review перед коммитом; установленный сервер и профили не заменяются.

## Причина и изменение

`prepare_stream` сохраняет в карте только пулы последовательностей текущего микробатча. При общем KV запрос может временно отсутствовать в микробатче, а его исходные K/G всё ещё находятся в KV. Когда запрос возвращается, для него требуется повторно сжать старые готовые пулы. Прежний расчёт `n_update` учитывает новые токены, границы последовательностей и dirty-записи, оставшиеся в карте. Потерянных записей в этом расчёте нет, поэтому `set_input` обнаруживает больше uncached pools, чем помещается в уже выделенный input tensor, и вызывает assert.

Добавлен общий `needs_rebuild(ctx, ubatch)`: по диапазонам позиций активных последовательностей оценивается число пулов, отсутствующих в persistent cache. Из диапазона вычитаются существующие cached-записи. Оценка консервативная: включает неполные крайние пулы и возможные отверстия. Когда она превышает incremental capacity, выбирается существующий full rebuild до построения/аллокации графа. Если буфер уже вмещает все `n_pools`, дополнительный rebuild не нужен. Один и тот же predicate используется при построении и в `can_reuse`, поэтому старый incremental graph не переиспользуется при недостаточной ёмкости. Reserve override сохранён.

Производственный diff: три файла, +55/-4 строки - `src/llama-kv-cache-kpool.h`, `src/llama-kv-cache-kpool.cpp`, `src/llama-graph.cpp`. Проверка `uncached.size() <= n_update` сохранена. Политика удаления записей, CUDA kernels, pooling-арифметика и masks не менялись. Сохранение пулов неактивных запросов потребовало бы отдельной политики вытеснения; в этот фикс оно не добавлено. Обычный decode продолжает использовать incremental-путь, а возвращение запроса может потребовать более дорогого rebuild. Ускорение не заявляется.

## Дополнительная защита MTP

Последний серверный контроль обнаружил отдельный assert `n_tps == 1` в MTP indexer reuse. Persistent top-k хранит один набор на KV-поток, а при unified KV несколько последовательностей используют один поток. Это воспроизведено и на прежней библиотеке в отдельной маленькой MTP-модели. Первая версия фикса ёмкости (V1) успешно устраняет DFlash abort, но этой защиты ещё не содержит.

В итоговом варианте reuse top-k разрешён только для раздельного KV или контекста с одним слотом. Для unified KV с несколькими слотами используется существующий путь пересчёта indexer на каждом MTP-шаге. Настройка MTP остаётся включённой; ускорение от reuse top-k в этой конфигурации отключено. Защита действует на весь такой контекст, включая временно одиночный активный запрос: это исключает чтение устаревшего selection после смены активных слотов.

CPU-контроли итогового варианта: MTP unified совпал побитово с принудительным fallback по 12 полным строкам logits; separated before/after точны по 12 строкам; unified single-slot before/after точны по 4 строкам. Callback подтверждает пересчёт K/G при unified multi-slot и сохранение reuse в двух поддерживаемых режимах. Основной pool replay повторён на итоговой библиотеке: прежние 46 строк и separated-контроль сохранены побитово. Оба существующих CPU-теста также повторно прошли.

## Проверка на небольшой модели

Harness использует существующий GGUF GLM5NEXT из `test-llama-archs` и настоящий `llama_decode` на CPU. Три разные истории предзаполняются раздельно; далее выполняются совместный decode, смена активных подмножеств, speculative suffix и rollback, удаление последовательностей и повторное заполнение. У успешного прогона 21 decode-вызов и 46 сохранённых строк logits.

| Контроль | Результат |
|---|---|
| Прежняя библиотека, unified KV | SIGABRT на том же `incremental pool-key update capacity is too small` при первом совместном decode |
| Фикс, unified KV | Все 21 вызов завершены |
| Фикс против полного пересчёта `LLAMA_GLM5_POOL_CACHE=0` | Все 46 полных строк logits побитово точны, max/RMS 0/0 |
| Раздельный KV до/после | Все 46 полных строк logits побитово точны |
| Callback без вмешательства в арифметику | Зафиксированы и full, и incremental операции; постоянный полный пересчёт не включён |
| Существующие `test-llama-archs -a glm5next -s 1234` и `test-recurrent-state-rollback` для GLM5NEXT | Оба прошли на CPU |

## Настоящая GLM-5.3-Flash

Проверка выполнена на прежней модели GLM-5.3-Flash-UD-Q4_K_XL с DFlash2-Q8_0 и встроенным MTP. Используются сохранённые payloads этапа 2: три serial запроса, две серии по три concurrent и три reuse запроса; до 64 токенов на ответ. Три слота, context8192, batch2048, ubatch64, F16 KV, текущие шесть GPU с фиксированными UUID и tensor split `1,1,1,1,1,0.4`, fit off. CUDA graphs работают в штатном режиме. Числа throughput не используются для вывода об ускорении.

| Серверный контроль | Результат |
|---|---|
| Прежняя библиотека, DFlash, unified KV | 3 serial ответа; SIGABRT на первой concurrent серии, тот же capacity assert, код -6 |
| V1, DFlash, unified KV | 12/12 запросов; штатное завершение, код 0 |
| V1, DFlash, unified KV, pool-cache выключен | 12/12 запросов; штатное завершение, код 0 |
| V1, DFlash, separated KV | 12/12 запросов; штатное завершение, код 0 |
| V1, встроенный MTP, unified KV | 3 serial ответа; отдельный SIGABRT `n_tps == 1` в top-k reuse |
| Итоговый фикс, встроенный MTP, unified KV | 12/12 запросов; штатное завершение, код 0 |

Итого 48 ответов в четырёх успешно завершённых серверных контролях и ещё шесть serial ответов двух аварийных контролей. DFlash-контроли выполнены на V1; после добавления защиты MTP основной CPU replay и существующие тесты повторены на итоговой библиотеке, серверный MTP контроль также повторён. Serial до/после совпадают в 3/3 случаях. DFlash unified с pool-cache и без него: 9/12 ответов совпадают по token IDs, тексту и stop-полям.

Три несовпавших ответа относятся к reuse. Для слотов 0/1 cache_n различается между контролями: 16/0 и 0/15; для слота 2 оба значения 0. Реальное разбиение concurrent батчей не фиксировалось, причина каждого различия не устанавливалась. Поэтому эти три ответа не доказывают ни побитовую эквивалентность pool-cache при restore, ни регрессию от данного фикса.

Совпадение последовательного и параллельного исполнения не является критерием этого фикса. В исправленном DFlash unified две параллельные серии совпали во всех трёх слотах, но serial/parallel и reuse/parallel различаются в слотах 0/1. Для оценки арифметики на одинаковом расписании используется побитовое сравнение CPU replay выше. Эти наблюдения не закрывают общий критерий эквивалентности speculative ответов при любом batching.

## Границы результата

Исправлены переполнение расчётной ёмкости pool-key update и недопустимый MTP top-k reuse при unified KV с несколькими слотами. Строгая диагностика `GGML_SCHED_DEBUG_REALLOC`, произвольные cache states и общая эквивалентность многослотовых speculative ответов остаются отдельными вопросами. К GLM-DSA (обычной GLM-5.3) этот pool-cache путь не относится. Остальные отложенные направления плана не возобновляются.

Сборки изолированы: `stage28/candidate-bin` хранит V1, `stage28/final-bin` - итоговый вариант с защитой MTP. Пересобраны только два затронутых CPP, остальные объекты проверены по SHA, включая KV-объект этапа 27. Основной build, `/home/sergei/_llama_cpp/my_build/llama-server` и активные INI не заменяются. Файлы в `tests/*` не добавлялись. GPU-процессы выполняются последовательно.
