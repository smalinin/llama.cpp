# Этап 5: CUDA Lightning Indexer и экспериментальный QSA Qwen4Exp

Этап 4 принят и закоммичен: `cc7bfba3b7013e1c2287f7602854c9d093ef32bc`. Review этапа 5 принят пользователем; разрешён коммит в ветке `my_build_upstream_20261007`. Проверки переноса завершены, но критерий включения нового QSA по умолчанию не выполнен: экспериментальный путь меняет часть ответов, а значительной экономии памяти всей модели не обнаружено.

По умолчанию сохранён прежний QSA. Для исследования нового пути используется `QWEN4EXP_FUSED_LID=1`; существующий `LLAMA_FUSED_LID_DISABLE=1` запрещает его и при этом флаге. Проверки sampling GLM-5.3 и DSpark DeepSeek-V4.1 остаются следующими пунктами после review этого этапа.

## Перенос и локальная адаптация

- [#29825](https://github.com/ggml-org/llama.cpp/pull/29825), `889edf43ddae0cfe9a4564a882764dc879759870`: поддержка четырёх голов Lightning Indexer в CUDA dispatch и проверке поддержки операции; в существующие backend-тесты добавлена форма с четырьмя головами.
- [#29901](https://github.com/ggml-org/llama.cpp/pull/29901), `1b43d311698269073fb4827db10f9d6f195d2e7d`: tile-ядро для восьми токенов одновременно, vector-ядро для меньших батчей. Варианты с 32/64 головами сохранены.
- Для F32/BF16 ключей сохранена их точность вместо сужения до F16. Они используют tile на 32 ключа, чтобы статическая shared memory оставалась меньше 48 КиБ; F16 и поддерживаемые квантованные типы используют 64 ключа.
- В локальном Qwen4Exp сохранены отдельные потоки, нормализация, RoPE, pooling, MTP selection reuse и прежний argsort. Индексатор получает веса голов, равные единице: локальные оценки не масштабируются на `1/sqrt(head_dim)`. Исходный конечный F32 bias видимости добавляется после fused op.
- Нулевая F16 маска получается из существующего конечного `blk_bias` через SCALE на ноль и cast. Это устраняет отдельный большой вход маски на каждом QSA-слое. Pooling разворачивается перед проекцией Q, сохраняя локальный порядок графа. Новый путь доступен только при `idx_dim=128`, четырёх головах и разрешённом fused LID.

Изменены три исходных файла: `ggml/src/ggml-cuda/lightning-indexer.cu`, `src/models/qwen4exp.cpp`, `tests/test-backend-ops.cpp`. Metal/Vulkan части upstream не переносились; AMD, Metal и Vulkan не проверялись.

| Итоговая замена маски против предыдущего экспериментального графа | 7872/7872 тензоров, logits и greedy токены совпали для 1/2 потоков |

Численный harness покрывает неполные tiles, batch 1/3/7/8/9/17, 1/4 потока, неконтинуальные F32 views, конечный bias `0/-1e9`, ReLU ties и большие F32 значения. Замаскированные элементы исключаются из NMSE, чтобы bias не скрывал ошибку. В обычных нетождественных оценках различие округления иногда переставляет близкие блоки: 337/298 позиций top-k с изменением порядка и 11/10 строк с изменением выбранного множества на двух GPU. Побитовое совпадение всех обычных top-k не заявляется.

CUDA-библиотеки совпадают по SHA256 во всех версиях после переноса, поэтому существующие backend-проверки относятся и к итоговым ядрам. После CTest менялись только экспериментальная ветвь QSA и её размещение буферов; итоговая сборка и захват default-пути проверены отдельно. Все 260 completion запросов пяти серий закончились успешно; это число не означает совпадения всех экспериментальных ответов с baseline.

## Почему экспериментальный путь меняет ответы

Прежний QSA использует cuBLAS MUL_MAT, разрешающий TF32. Новое ядро считает произведения в FP32. Replay реальных фиксированных Q/K против CPU подтвердил различие точности:

| Replay | NMSE прежнего пути с TF32 | NMSE прежнего пути при `NVIDIA_TF32_OVERRIDE=0` | NMSE fused пути |
| --- | --- | --- | --- |
| step 0, 64 блока, batch 128 | `3.19e-9` | `4.39e-15` | `1.34e-14` |
| step 31, 1024 блока, batch 128 | `8.52e-9` | `1.57e-14` | `1.57e-14` |

С TF32 изменились порядок top-k в 6/27 позициях и множество в 0/1 строках; при отключении TF32 в этих двух replay изменений выбора не было. Это изолированная проверка причины расхождения оценок, а не доказательство совпадения всей модели при глобальном отключении TF32. Изменение качества ответов не оценивалось.

В итоговой экспериментальной серии на 64K расходятся 26/40 ответов и 18 наборов draft-счётчиков. Для одного слота без MTP короткий prompt совпал, длинный prompt на 13117 токенов расходится с первого выходного токена. Счётчики и скорости при различных выходах нельзя использовать как доказательство ускорения. Новый путь оставлен выключенным по умолчанию.

## Память и условия измерения

После замены GPU использованы пять RTX 4090/4090 D по 49140 МиБ и RTX 3090 на 24576 МиБ, power limit 280 W, CUDA 13.0. GPU UUID, boot ID, реальные слои, модельные буферы и загруженные библиотеки сохранены в manifest каждого запуска. Они совпадают в сравниваемых парах. Модель: `Qwen3.8-Flash-Next-UD-Q4_K_XL`, локальная архитектура Qwen4Exp; MTP с отдельным draft. Параметры: layer split `1,1,1,1,1,0.4`, F16 target/draft KV, batch 2048, ubatch 512, 12 потоков, fit off.

Baseline, первоначальный эксперимент и default gate проверены на контекстах 8192/65536, одном/четырёх слотах, MTP off/on. Для итогового экспериментального графа повторены четыре конфигурации 65536. Запросы greedy, `cache_prompt=false`, 64 выходных токена, по два полных prefill повтора на prompt и слот; многослотовые запросы выполнялись одновременно с явными slot IDs. Короткий prompt содержит 1697 токенов, длинный 13117. C++ capture использует отдельный prompt на 4311 токенов и другой ubatch; его callback меняет планирование, поэтому время capture не является замером производительности.

Изолированный allocator графа оценок QSA уменьшился на 67-71%. Например, при одном потоке и batch 512:

| Число блоков | Прежний буфер, МиБ | Итоговый fused буфер, МиБ |
| --- | ---: | ---: |
| 2048 | 39.00 | 12.01 |
| 16384 | 305.00 | 89.01 |
| 65536 | 1217.00 | 353.01 |

Число блоков в изолированном тесте не равно размеру контекста модели. В реальном сервере итоговая экономия намного меньше:

| Контекст / слоты / MTP | Сумма CUDA compute до, МиБ | После, МиБ | Изменение, МиБ | Наблюдаемый суммарный пик VRAM до / после, МиБ |
| --- | ---: | ---: | ---: | ---: |
| 65536 / 1 / off | 8707.07 | 8691.15 | -15.92 | 92648 / 92632 |
| 65536 / 1 / on | 8707.07 | 8691.15 | -15.92 | 96392 / 96462 |
| 65536 / 4 / off | 3437.44 | 3437.52 | +0.08 | 86624 / 86572 |
| 65536 / 4 / on | 3437.44 | 3437.52 | +0.08 | 92434 / 92384 |

Пик VRAM вычислен как максимум суммы шести GPU в одном наблюдаемом sample, а не сумма отдельных максимумов. Мониторинг дискретный, включает загрузку и выполнение; изменения на десятки МиБ не доказывают существенной экономии всей модели. На default-пути размеры compute buffer совпали во всех восьми конфигурациях. Пиковый RSS каждого процесса также сохранён в JSON; при разных экспериментальных ответах его колебания не интерпретируются как выигрыш.

Первый вариант с отдельной zero-mask leaf увеличивал полный compute buffer. Последняя адаптация убрала лишние входы маски и 192 МиБ относительно промежуточного эксперимента на 64K/одном слоте. Относительно этапа 4 остаётся лишь -15.92 МиБ, около 0.18% compute buffer. Ускорение всей модели и существенная экономия её VRAM не подтверждены.
