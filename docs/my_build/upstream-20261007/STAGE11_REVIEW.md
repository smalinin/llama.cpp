# Этап 11: источник усиления различий в FFN DeepSeek-V4.1

Этап 10 закоммичен по указанию пользователя: `1ffcefe92`, `docs : record DeepSeek V4.1 attention and quantization diagnosis`. Продолжена диагностика FFN слоя 2 на том же кандидате.

На строго одинаковом входе scalar и batched FFN дают разные промежуточные активации. Два значения после SwiGLU пересекают границу округления Q8_1 у эксперта 217; это объясняет почти всю разницу FFN около 2,5e-5. Штатный CUDA-квантователь и независимый CPU-расчёт по настоящим Q3_K-весам подтверждают механизм. Это локализованный численный эффект; полная совместимость greedy off/on и ускорение DSpark остаются открытыми. Производственного патча этого этапа нет.

Подготовлено для review перед следующим коммитом. Установленный сервер, рабочие профили и исходники вычислительных ядер не менялись.

## Как воспроизведён настоящий FFN

- Ветка `my_build_upstream_20261007`, HEAD `1ffcefe92`; неизменяемые библиотеки `stage8/candidate-bin`, проверены все 32 SHA256.
- Оригинальный DeepSeek-V4.1 Q2_K/Q8_0 Engram. Входы `ffn_norm-2` и контрольные выходы `ffn_out-2` взяты с первого decode-вызова этапа 10, режим FP32 floating MUL_MAT плюс scalar Flash Attention, widths 1/2/4.
- Из GGUF напрямую загружены все 384 эксперта слоя 2: Q2_K up/gate, Q3_K down; BF16 router, routing bias, Q5_K shared up/gate и Q6_K shared down. Записаны offsets, размеры и SHA каждого тензора. В конце этапа исходные байты весов повторно хешированы.
- Граф повторяет sqrt/softplus routing, top-6, нормализацию весов с clamp 6,103515625e-5, scaling 1,5, SwiGLU clamp 10, сумму routed-экспертов и shared-эксперт. Явный FP32 router сохранён; CUDA Graphs отключены. Графы для widths 1/2/4 сохраняют штатный выбор CUDA fusion.
- Проверены RTX 4090/D Ada UUID `GPU-3972c9ef-dd88-6b95-ac0c-fc9b0eb86f76` и RTX 3090 Ampere UUID `GPU-a84e3bf7-a50b-c880-8a79-7a7f81544783`. Draft и остальные слои модели не загружались.

**Все шесть полных выходных матриц FFN совпали побайтно с модельным capture:** widths 1/2/4 на обеих архитектурах. Контроль с профилировщиком также сохранил все байты выходных файлов обычного Ada replay.

Для каждого из трёх сохранённых входов его первый токен отдельно скопирован во все колонки widths 1/2/4. Повторы и одинаковые колонки внутри каждого варианта совпадают побайтно. Выбор экспертов первого токена неизменен: `[178,42,217,36,334,131]`.

## Разница сохраняется на одинаковом входе

Первый сохранённый вход, width 2 против scalar; width 4 даёт те же значения. На Ada и Ampere результат одинаков в приведённых метриках.

| Граница | Max разница | RMS |
| --- | ---: | ---: |
| Router logits | 9,53674e-7 | 2,63628e-7 |
| Нормализованные routing weights | 2,98023e-8 | 1,21667e-8 |
| Routed hidden после SwiGLU | 1,78814e-7 | 8,05281e-9 |
| Shared hidden после SwiGLU | 0 | 0 |
| Сумма routed-экспертов | 2,49594e-5 | 6,70334e-6 |
| Полный FFN output | 2,49594e-5 | 6,70331e-6 |

Следовательно, малая разница входов FFN, унаследованная от HC, не является необходимым условием этого локального усиления. При её устранении разница остаётся внутри FFN. Отключение CUDA fusion её также не устраняет; это не основание выключать fusion в рабочем сервере.

## Два перехода через границу Q8_1

В отдельном harness вызвана **функция `quantize_row_q8_1_cuda` из тех же библиотек**, на сохранённых routed-hidden активациях. Сняты реальные Q8_1-байты с padding 2560; сравниваются 2304 полезных значения каждого из шести экспертов. Это повторный запуск штатного квантователя на capture, а не чтение временного буфера из полного модельного графа.

При width 2/4 против scalar изменились только два целых значения, оба у slot 2, эксперт 217:

| Offset внутри hidden эксперта | Scalar Q8 | Batched Q8 |
| --- | ---: | ---: |
| 513 | 35 | 34 |
| 1624 | -73 | -72 |

Half scale `d` и half sum не изменились. Ada/Ampere Q8_1-буферы совпадают целиком, повторы стабильны. CPU-эмуляция уравнений квантователя совпала со всеми захваченными integer/scale полями широких вариантов.

Далее IDs и routing weights зафиксированы по scalar; отдельному down-графу подставлены scalar или batched hidden. При неизменных hidden ширина down-графа меняет результат всего на **2,98023e-8**. Замена hidden на batched при той же scalar down-арифметике даёт **2,49669e-5**. Значит, основное усиление связано с изменением квантованных активаций до down, а не с собственной batch-зависимостью down-редукции.

Для эксперта 217 извлечены оригинальные Q3_K-веса. CPU double projection разности захваченных Q8_1-активаций, умноженной на фиксированный routing weight, предсказывает max **2,49665e-5**. Остаток относительно GPU down-контроля: max **2,49161e-8**, RMS **2,86826e-9**. Относительно разности полного routed FFN с его настоящими routing weights остаток max **2,93312e-8**.

Контроль с теми же деквантованными Q3_K-весами и исходными F32 hidden, без Q8_1 округления, даёт разность max **6,70077e-9**. Это локальный контроль одной проекции; он не заменяет target другим checkpoint и не измеряет качество всей модели.

## Какие ядра участвуют

Nsight Systems записал 22 вычисления FFN. Для routed Q2_K up/gate/SwiGLU:

- Scalar: `mul_mat_vec_q<Q2_K,1,true,...>`, блок `[32,4,1]`, четыре warp участвуют в редукции одного токена.
- Width 2/4: `mul_mat_vec_q_moe<Q2_K,2,true>`, блок `[32,2,1]` или `[32,4,1]`; каждый warp считает отдельный токен, редукция внутри warp.

Это разные порядки суммирования. Профиль вместе с кодом `mmvq.cu` объясняет, почему fusion может сохраняться, а малая разница активаций остаётся. Отключение fusion подтверждает, что одной причиной в fused SwiGLU эффект не ограничивается. Этап не устанавливает нарушение заявленного FP32-контракта: routed matmuls используют квантованные веса и штатный Q8_1-путь.

На проверенной конфигурации 384-expert top-k fusion и fused down-Q reduction **не включены**. В текущем коде первый требует `GGML_CUDA_TOPK_MOE_384`, а шестёрка экспертов для второго требует `GGML_CUDA_MOE_DOWN_REDUCE_EXTENDED`. Профиль показывает обычный top-k, отдельную Q3_K down-проекцию и batched `moe_weighted_reduction_f32`. Нельзя приписывать наблюдаемый эффект этим двум выключенным оптимизациям.

Источник: [ядра, launch dimensions и времена](stage11/kernel-summary.json). Суммарные kernel times используются для идентификации, не как throughput всей модели.

## Стоимость последовательного FFN

На фиксированном входе выполнено по 10 прогревочных вызовов и пять групп по 100 вызовов для каждой ширины. CUDA Graphs отключены; измерено синхронизированное host wall time, приведена медиана средних времён групп.

| GPU | Один scalar FFN, мс | Width 2, мс | Width 4, мс | Оценка 2 scalar / width 2 | Оценка 4 scalar / width 4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Ada | 0,1900 | 0,2434 | 0,3729 | 1,56x | 2,04x |
| Ampere | 0,3179 | 0,4358 | 0,7083 | 1,46x | 1,80x |

Последние столбцы вычислены как `width * T_scalar / T_width`. Это оценка стоимости последовательного выполнения **всего** FFN, не реализованного обхода только up/gate и не замер HTTP tokens/s. Порядок widths последовательный, частоты GPU не фиксировались; это предварительная оценка локальной стоимости. Она не обосновывает перенос полного scalar FFN в рабочий DSpark.

Источник: [benchmark summary](stage11/benchmark-summary.json), [harness](stage11/ffn-bench.cpp), сырые группы `bench-*/timings.jsonl`.

## Решение и следующий шаг

Локальный механизм FFN слоя 2 подтверждён на одинаковых входах с сохранёнными экспертами и штатным up/gate fusion. Полный scalar FFN как производственное исправление не предлагается: локальная стоимость выше, другие источники batch-зависимости attention/HC/router сохраняются.

Следующий шаг после review: проверить узкий вариант согласования арифметики scalar/batched routed up/gate, отдельно измерить его стоимость, затем проверить остаточную цепочку и свободную greedy off/on генерацию на нескольких prompt. Изменение одного ядра нельзя считать исправлением всей совместимости DSpark без этих проверок.

Большие tensor dumps, оригинальные веса, бинарники и Nsight traces остаются в локальной папке `stage11/`; Git содержит исходники воспроизведения, хеши, manifests, численные сводки и результаты. Первые попытки с чтением elided shared-down intermediate исключены и заменены чистыми replay; исправление размера индекса сделано до GPU-запусков. См. [excluded-attempts.json](stage11/excluded-attempts.json).
