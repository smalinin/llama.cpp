# Этап 4: оптимизации CUDA

Рабочая версия поверх принятого коммита этапа 3 `0a1ad5457170f3f99318e89b2e36d40fd4cc1685`, ветка `my_build_upstream_20261007`. Review этапа 4 принят пользователем; коммит `cc7bfba3b7013e1c2287f7602854c9d093ef32bc`. Этап 5 начат отдельно.

## Восстановление после перезагрузки

8 октября 2026 года проверены исходники и сохранённые бинарники: diff совпал с сохранённым, SHA256 обеих версий библиотек и инструментов совпали. Повторная CUDA Release сборка прошла без изменений бинарников. Часть прежних логов оказалась пустой или неполной; они перенесены в `stage4/interrupted-20261007/` и исключены из результатов.

Новая конфигурация: пять RTX 4090/4090 D по 49140 MiB и RTX 3090 с 24576 MiB. Прежняя карта с 20480 MiB заменена на RTX 4090 D; изменились индексы. Порядок устройств для моделей закреплён UUID, эквивалент текущим индексам `2,1,0,5,4,3`. Обе сравниваемые версии запускаются на этой конфигурации; замеры до замены карты не используются. Driver 580.159.04, CUDA toolkit 13.0; power limit 280 W на всех картах.

## Изменения

Перенесены без конфликтов:

- [#29393](https://github.com/ggml-org/llama.cpp/pull/29393), `1ab7e5ad2d4e7295c94c3b966a3e0b70fa365865`: CUDA объединяет RMS_NORM и следующий SCALE при нулевом bias, F32 и допустимых потребителях промежуточного результата. Умножение scale выполняется после результата нормализации, сохраняя обычный порядок округления.
- [#29633](https://github.com/ggml-org/llama.cpp/pull/29633), `9d3aba6b5e10a6dd086bd0555bd12c00366a8916`: узкие FP16/BF16 матрицы используют MMVF до батча 8, когда MMF неприменим. Для поддерживаемых MMF форм и больших батчей выбор не меняется.

Изменены пять CUDA-файлов: 94 добавленные и 25 удалённые строки. Локальные модели, MTP/DSpark, sparse attention и размещение памяти не изменены. AMD-ветки перенесены, но на AMD не проверялись.

## Корректность

- CUDA Release сборка после перезагрузки прошла.
- 9/9 профильных CTest прошли.
- Существующие RMS_NORM, SCALE и соседние norm-fusion тесты: 229/229 на каждой версии и каждом из GPU sm_89/sm_86, всего 916 проверок.
- Standalone GGML harness: 528 сценариев на каждой версии и каждом из GPU sm_89/sm_86; дополнительно 528 при отключённом fusion на новой версии и 120 сценариев padding/permute на каждой версии и каждом GPU. Всего **3120 сравнений с CPU**, все прошли.
- Проверены размеры RMS_NORM 1/32/128/1023/1024/4096, нулевой/отрицательный/положительный scale, нулевой/ненулевой bias, views и несколько потребителей. Матрицы FP16/BF16: K 128/130, M 32/33/511/512/513/1024, батчи 1/2/3/4/8/9/16/32, одна и четыре головы; отдельно padding и permute.

Нормализация численно совпала во всех 144 сценариях до/после на обоих GPU. В 12 сценариях с нулевым scale отличаются только знаки нулей; максимальная абсолютная разница равна 0. Остальные 132 сценария совпали побайтово, в том числе с отключённым fusion. Для матриц изменение ядра меняет округление в части сценариев; сравнение с CPU прошло с допуском существующих MUL_MAT тестов NMSE < 5e-4.

**Существующее ограничение MMF:** валидная FP16 матрица K=128, M=512, четыре головы, батч 4, stride строки 260 байт вызывает `GGML_ASSERT(stride_row % 2 == 0)` внутри MMF на обеих версиях. Патчи его не устраняют; оно не включено в число прошедших случаев. Файл воспроизведения: [mat-existing-stride-assert.txt](stage4/mat-existing-stride-assert.txt).

В первой попытке generic backend tester давал NaN в CPU и CUDA для некоторых padded views. Причина этих NaN не установлена; эти прогоны исключены. Контрольный harness явно инициализирует весь backing tensor конечными значениями, проверяет конечность результата и проходит для тех же padding/permute форм.

## Замеры отдельных операций

Nsight Systems, RTX 4090, CUDA Graphs отключены, 503 вычисления каждого графа:

| Граф | CUDA-ядер до | CUDA-ядер после | Суммарное GPU-время до | После |
| --- | ---: | ---: | ---: | ---: |
| RMS_NORM + SCALE, F32 [128,512] | 1006 | 503 | 1,456 мс | 0,868 мс |
| MUL_MAT, FP16 [128,33] x F32 [128,4] | 2012 | 503 | 3,481 мс | 0,959 мс |

В первом случае два запуска заменены одним; во втором устранены два преобразования типов и cuBLAS split-K reduction, остаётся один MMVF. Это измерения выбранных небольших графов, не оценка ускорения всей модели.

Существующий `test-backend-ops perf`: три прогона каждой версии, чередование до/после, медианы:

| GPU | FP16 узкая матрица, мкс до/после | Ускорение | BF16 узкая матрица, мкс до/после | Ускорение |
| --- | ---: | ---: | ---: | ---: |
| RTX 4090 | 7,32 / 2,24 | 3,27x | 3,10 / 2,23 | 1,39x |
| RTX 3090 | 6,18 / 2,87 | 2,15x | 3,87 / 2,86 | 1,35x |

Форма: K=128, M=33, батч 4. Соседние MMF M=32 и prefill батч 32: медианы изменились не более чем на 1%. Подробные три значения каждого режима сохранены в [mat-performance.json](stage4/mat-performance.json).

## Реальные модели

Основная серия завершена: 16 запусков, 112 completion запросов. **56/56 пар ответов до/после совпали по token IDs и тексту**, включая 40 greedy и 16 sampling. **56/56 пар счётчиков draft/accepted совпали**. Параметры, GPU UUID, boot ID, фактическое размещение слоёв и model buffers совпали во всех 8 парах запусков. Загруженные библиотеки проверены по `/proc/PID/maps` и SHA256. Подробные значения: [real-results.md](stage4/real-results.md), [real-comparison.json](stage4/real-comparison.json).

Сравнивались GLM5NEXT, Qwen4Exp, обычный GLM-5.3 GLM-DSA и DeepSeek-V4.1, MTP/DSpark off/on. Для GLM5NEXT/Qwen фиксирован split `1,1,1,1,1,0.4`, все слои GPU; для крупных GLM-DSA/DeepSeek применяется fit с одинаковым запасом памяти. Реальное размещение слоёв и загруженные библиотеки сохраняются в каждом manifest.

Контекст 8192, batch 2048, ubatch 512, F16 target/draft KV, один слот, 12 CPU threads. Короткий исходный prompt из 96 фактов: два greedy и два sampling запроса с seed 1234. Для Qwen/GLM5NEXT добавлены ещё два коротких greedy и четыре greedy запроса на prompt из 300 фактов. Для оценки времени первого запроса и последующих прогретых запросов используются отдельные группы.

По GLM5NEXT/Qwen изменения prefill/decode находятся в пределах примерно +/-2%; устойчивое ускорение всей модели не установлено. У DeepSeek без DSpark prefill/decode -0,14% / -0,22%, с DSpark +0,07% / -1,31% в коротком контроле. Для GLM-DSA с MTP -0,52% / +0,33%. Основные GLM-DSA/DeepSeek оценки основаны на одном прогретом greedy замере; статистическую значимость этих небольших отклонений установить нельзя.

В одном основном GLM-DSA native замере decode снизился на 7,70%, поэтому выполнен дополнительный контроль: warmup и шесть одинаковых greedy запросов на каждой версии, без изменения настроек или `cache_prompt=false`. Все **7/7 пар ответов совпали**, фактическое размещение одинаковое. Медиана последних пяти запросов: prefill 141,08 / 140,73 токена/с (-0,25%); decode 12,87 / 12,92 токена/с (+0,41%). Первоначальное снижение не повторилось. Это ещё 14 completion запросов сверх основной серии, всего **126 запросов, 63 совпавшие пары**. Данные: [dsa-validation-comparison.json](stage4/dsa-validation-comparison.json).

Проверка воспроизводимости sampling GLM-5.3 и диагностика DSpark остаются завершающими пунктами плана; данный этап не заменяет их. Ограничение DeepSeek native continuation после restore из этапа 3 остаётся открытым.

## Решение для review

Оба небольших CUDA backport сохранены. Численная корректность, повторные матричные замеры и проверки реальных моделей прошли; выигрыш на выбранных узких матрицах воспроизводится, заметной регрессии в измеренных соседних режимах не обнаружено. Для используемых моделей выигрыш 4–5% prefill из upstream не подтвердился. Ограничение старого MMF stride, знаки нулей при SCALE и отсутствие AMD проверки описаны выше.

Review этапа 4 принят пользователем, изменения закоммичены (`cc7bfba3b`). Следующий этап: уменьшение памяти индексатора Qwen4Exp.
